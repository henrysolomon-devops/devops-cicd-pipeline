# v5.1: Migrate all environments to AWS EC2/k3s

**Concept demonstrated:** Extending an existing CI/CD pipeline to a real cloud target

## Why this version?

Through v5, the EC2/k3s server existed but wasn't part of the automated pipeline - it was built, tested manually, and torn down. Meanwhile, `dev`, `staging`, and `production` still lived on a local `kind` cluster.

v5.1 closes that gap: all three environments now live permanently on the same EC2/k3s server, and `deploy.yml` deploys onto it directly. The local `kind` cluster and the self-hosted runner are both retired - the whole pipeline runs entirely in the cloud, with nothing depending on this machine being on.

## Two workflows, two different risk levels

Building/destroying a real server costs money and can't be undone by accident, so it's kept completely separate from the automatic app deploys, which cost nothing and should happen on every push.

### `infra.yml` - manual, for the server itself

Triggered only by hand (`workflow_dispatch`), never by a push. Picks `apply` or `destroy`, gated behind the `aws-infra` environment so it always waits for manual approval before touching anything real.

- Authenticates to AWS via **OIDC** - GitHub issues a short-lived token proving the run genuinely comes from this repo, and AWS trusts it enough to hand out temporary credentials. No AWS access key is stored anywhere.
- Runs `terraform apply`/`destroy`, then Ansible to install k3s
- Creates the `dev`/`staging`/`production` namespaces on the server
- Saves the resulting kubeconfig as a repo secret (`KUBECONFIG_B64`) and the security group ID as a repo variable (`SECURITY_GROUP_ID`), so `deploy.yml` always has what it needs without any manual copy-pasting

### `deploy.yml` - automatic, for the app

Still triggers on every push to `main`, same as v4. The chain is:

```
build → infra-check → deploy-dev → deploy-staging → deploy-production
```

`infra-check` is new: an empty job gated behind its own environment, so the pipeline always pauses right after the build to confirm the AWS server is actually up (via `infra.yml`) before anything tries to deploy onto it. `dev` still deploys automatically once that's confirmed; `staging` and `production` still each require their own separate approval, same as v4.

Every deploy job now runs on a GitHub-hosted runner instead of the old self-hosted one, since the target (a public EC2 server) is reachable from anywhere, not just this machine.

## Terraform state moved to S3

GitHub-hosted runners don't keep a persistent local disk between runs, so the local `terraform.tfstate` file from v5 wouldn't survive from one run to the next. State now lives in an S3 bucket, with Terraform's native S3 locking (1.10+) instead of a separate DynamoDB table.

## Security group: permanent access for me, temporary access for GitHub

The security group has two kinds of rules:

- **Permanent**: my own IP always has access to SSH, the app ports (5000-5002), and the k3s API - so I can check things in a browser or run `kubectl` manually anytime.
- **Temporary, per-run**: GitHub's runners have no fixed IP, so instead of opening the security group to a broad, ever-changing range, each workflow run opens access just for its own current IP right before it needs it, and closes it again immediately after - via the AWS CLI, using the same OIDC credentials as the rest of the run.

## One port per environment

All three environments now live on the same server and the same public IP, so each needs its own port to stay reachable separately:

| Environment | Port |
|---|---|
| dev | 5000 |
| staging | 5001 |
| production | 5002 |

Each `values-<env>.yaml` sets its own `service.port`, and `service.type` is `LoadBalancer` everywhere - k3s's built-in Klipper load balancer exposes each Service on the node's public IP directly, no external AWS load balancer needed.

## What changed from v5

- `terraform/backend.tf` (new): points Terraform's state at the S3 bucket
- `terraform/security.tf`: rewritten around the permanent/temporary split above
- `.github/workflows/infra.yml` (new): manual apply/destroy via OIDC
- `.github/workflows/deploy.yml`: self-hosted → GitHub-hosted, `kind` → the EC2/k3s server, new `infra-check` gate
- `helm/devops-pipeline/values.yaml` and each `values-<env>.yaml`: image now pulled from `ghcr.io` instead of a local image, `service.type` is `LoadBalancer`, each environment has its own port
- `values-ec2.yaml` removed - no longer needed now that all three environments live on the server permanently, rather than a one-off manual test override

## Setting this up from scratch (for anyone forking this project)

1. **One-time AWS setup:**
   - Create an IAM OIDC identity provider for `token.actions.githubusercontent.com` (audience `sts.amazonaws.com`)
   - Create an IAM role trusting that provider, scoped to this repo's `main` branch and its `aws-infra`/`dev`/`staging`/`production` environments, with EC2 and S3 permissions
   - Create an S3 bucket for Terraform state (versioning on)
2. **GitHub repo setup:**
   - Environments: `aws-infra`, `infra-check`, `dev`, `staging`, `production` (all but `dev` need a required reviewer)
   - Variables: `MY_IP`, `SSH_PUBLIC_KEY`
   - Secrets: `SSH_PRIVATE_KEY`, and a fine-grained PAT with repo-scoped Secrets + Variables read/write access, stored as `ADMIN_PAT`
   - `KUBECONFIG_B64` and `SECURITY_GROUP_ID` don't need to be set manually - `infra.yml` creates and maintains them automatically the first time it runs
3. Run `infra.yml` with `apply` to build the server
4. Push to `main` (or run `deploy.yml` manually) to deploy the app

## Testing

```bash
ssh -i ~/.ssh/devops-pipeline-key ubuntu@<server-ip>
sudo k3s kubectl get pods -A
sudo k3s kubectl get svc -A
```

Then, from a browser:

```
http://<server-ip>:5000/   → dev
http://<server-ip>:5001/   → staging
http://<server-ip>:5002/   → production
```

Each one was confirmed to show the correct `Environment`, a real Pod hostname, and a `healthy` status - the same checks used in every version since v1, just pointed at a real cloud server this time.

Self-healing was re-verified the same way as v2: deleting a Pod on the new cluster and confirming Kubernetes replaced it automatically. Replica counts were confirmed to match each environment's `values-<env>.yaml` (1 in dev, 2 in staging, 3 in production).

The full pipeline was also triggered by a real push to `main`, confirming `infra-check` correctly pauses for approval, `dev` deploys automatically once cleared, and `staging`/`production` each pause for their own separate approval before deploying.

## Cost and safety

Same rule as v5: the server is never left running by accident. `infra.yml`'s `destroy` option tears down all 9 resources cleanly, run manually whenever the server isn't actively needed.
