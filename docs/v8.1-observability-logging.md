# v8.1: Loki + Grafana Alloy + Alertmanager (Log Aggregation & Alerting)

**Concept demonstrated:** Log aggregation and alerting

## Why Loki, Alloy, and Alertmanager?

v8 gave the project real observability into *how* the system is behaving -
request rates, latency, error counts. What it couldn't answer was *why*
something went wrong, since none of that data included the actual log
output, and there was no way to be notified when a metric crossed into
problem territory without staring at a dashboard. v8.1 closes both gaps at
once: Loki and Grafana Alloy bring the app's and cluster's log output into
Grafana alongside the metrics already there, and Alertmanager (bundled with
`kube-prometheus-stack` since v8 but left disabled until now) turns metric
thresholds into actual notifications.

These two capabilities were built together deliberately - alerting without a
fast way to see the logs behind an alert has limited value, so it made more
sense to add both at once than to ship alerting alone and log aggregation
later.

## Key concepts

- **Log aggregation vs. metrics**: metrics are numbers sampled over time
  (request count, latency); logs are the raw text output of a running
  process. Prometheus handles the former, Loki the latter - two different
  tools because they're fundamentally different kinds of data.
- **Loki's index-light design**: unlike Elasticsearch, Loki only indexes
  metadata (labels like `namespace`, `pod`, `container`), not the full text
  of every log line. That keeps it lightweight and cheap to run, at the cost
  of full-text search performance - a reasonable tradeoff here, since
  filtering by namespace and reading recent output is the actual use case.
- **Grafana Alloy**: the agent that actually reads container logs off the
  Node and ships them to Loki. Loki only stores what it's given; something
  else has to do the collecting. Alloy is the current standard for this,
  replacing the older Promtail, which reached end-of-life on March 2, 2026.
- **Alertmanager routing**: Prometheus fires alerts based on rules, but it's
  Alertmanager that decides where a firing alert actually goes - which
  channel, grouped how, how often repeated. Routing here is driven entirely
  by a `team` label (`infra` or `app`) set on every alerting rule.

## What's included

- **Loki** (single-binary mode, since this project only ever runs on one
  Node), storing log chunks in a dedicated S3 bucket rather than local disk,
  so log history survives a `terraform destroy`/`apply` cycle the same way
  Terraform's own state already does.
- **Grafana Alloy**, running as a DaemonSet, discovering every Pod across
  every namespace through the Kubernetes API and forwarding their logs to
  Loki with `namespace`, `pod`, and `container` attached as labels.
- **Alertmanager**, routing to two separate Slack channels based on a `team`
  label:
  - `#alerts-infra` - disk pressure, memory pressure, crash-looping Pods,
    Pods stuck in a bad phase
  - `#alerts-app` - high HTTP error rate, slow or failing Open-Meteo calls,
    a sustained low Redis cache hit ratio
- **A live logs panel** on the existing app dashboard
  (`devops-pipeline: App Metrics`), using the same `$environment` dropdown
  already used by every metric panel, so switching environments filters
  logs and metrics together.

## What changed from v8

- `terraform/iam.tf` (new): an IAM Role and Instance Profile scoped to only
  the Loki S3 bucket, attached to the EC2 instance. k3s has no IRSA (that's
  EKS-only), so an Instance Profile on the instance itself is how Loki gets
  AWS credentials without any key ever being stored in the cluster.
- `terraform/compute.tf`: attaches the new Instance Profile, and raises the
  IMDS hop limit to 2 - Loki runs inside a container, one network layer
  deeper than the instance itself, and the default hop limit of 1 silently
  blocks containerized workloads from reaching the metadata service.
- `monitoring/loki-values.yaml`, `monitoring/alloy-values.yaml` (new): Helm
  values for Loki and Alloy.
- `monitoring/alertmanager-config.yaml` (new): the two-channel Slack routing
  config, merged into `kube-prometheus-stack`'s own values as a second Helm
  `-f` file. Webhook URLs are never committed - the file holds placeholders,
  substituted from repo secrets at apply time.
- `monitoring/prometheusrule-infra.yaml` (new): cluster-level alerting
  rules, applied directly rather than through a Helm chart, since they
  watch the whole cluster rather than belonging to one Release.
- `helm/devops-pipeline/templates/prometheusrule-app.yaml` (new):
  application-level alerting rules, deployed once per environment
  alongside the rest of the app chart.
- `monitoring/values.yaml`: Alertmanager enabled; `ruleSelectorNilUsesHelmValues`
  and `ruleNamespaceSelector` relaxed (the same class of setting already
  needed for ServiceMonitor discovery in v8, now needed for PrometheusRule
  discovery too); the control-plane components kube-prometheus-stack
  expects by default (`kubeScheduler`, `kubeControllerManager`, `kubeEtcd`,
  `kubeProxy`) disabled, since k3s doesn't expose any of them the way a
  standard kubeadm cluster does; a Loki datasource registered in Grafana
  with a fixed `uid` so dashboard panels can reference it reliably across
  every rebuild.
- `helm/devops-pipeline/dashboards/app-metrics.json`: a new "Live Logs"
  panel added to the existing dashboard.
- `.github/workflows/infra.yml`: installs Loki and Alloy, renders the
  Alertmanager Slack config from repo secrets, and applies the infra-level
  PrometheusRule - all as part of the existing `apply` path.
- `terraform/security.tf`: unchanged - Loki and Alloy are never reachable
  from outside the cluster, so no new ingress rule was needed.

## Setup

Nothing to run by hand for most of this - Loki, Alloy, and the infra-level
alerting rules all install automatically as part of `infra.yml`'s `apply`
path, the same as the rest of the monitoring stack since v8.

Two one-time steps are required before the first `apply`, though:

**1. The Loki S3 bucket.** Unlike everything else Terraform manages, this
bucket is created once, by hand, outside Terraform entirely - the same
pattern already used for the Terraform state bucket in v5.1. It has to live
outside the regular destroy/apply cycle, or every `terraform destroy` would
wipe out the log history that's the entire point of storing it in S3:

```bash
aws s3api create-bucket \
  --bucket devops-cicd-pipeline-loki-logs \
  --region us-east-1

aws s3api put-public-access-block \
  --bucket devops-cicd-pipeline-loki-logs \
  --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
```

Then, in the S3 console, add a lifecycle rule on the bucket expiring
objects after 14 days - old log chunks have no long-term value here, and
this keeps the bucket from growing indefinitely.

**2. IAM permissions for the OIDC role.** The `github-actions-terraform-role`
used by `infra.yml` needs permission to create and manage the new IAM Role
and Instance Profile - it only had EC2 and S3-state permissions before this
version. Create and attach a policy scoped to just that one Role and
Instance Profile:

```bash
aws iam create-policy \
  --policy-name loki-iam-management \
  --policy-document file://loki-iam-management-policy.json

aws iam attach-role-policy \
  --role-name github-actions-terraform-role \
  --policy-arn arn:aws:iam::<account-id>:policy/loki-iam-management
```

**3. Slack webhooks.** Create two Incoming Webhooks in Slack (one per
channel - `#alerts-infra` and `#alerts-app`), then add them as repo
secrets under **Settings → Secrets and variables → Actions**:

- `SLACK_WEBHOOK_INFRA`
- `SLACK_WEBHOOK_APP`

## Testing

**1. Bring up the infrastructure:**

```
# infra.yml -> apply
```

This provisions the server, installs k3s, `kube-prometheus-stack`, Loki,
Alloy, and ArgoCD, and applies the infra-level alerting rules - no manual
steps after this.

**2. Confirm Loki and Alloy are healthy:**

```bash
ssh -i ~/.ssh/devops-pipeline-key ubuntu@<server-ip>
sudo k3s kubectl get pods -n monitoring
```

`loki-0` and the `alloy-...` Pod should both show `2/2 Running`.

**3. View live logs in Grafana:**

```
http://<server-ip>:3000
```

Open **Dashboards → devops-pipeline: App Metrics**, and use the
**Live Logs** panel at the bottom. Switching the `$environment` dropdown
at the top filters logs the same way it already filters every metric
panel above it.

**4. Confirm logs persist across a destroy/apply cycle:**

Widen the panel's time range beyond how long the current server has been
up (for example, to the last 24 hours). Log lines with timestamps older
than the current server's uptime confirm they're being read back from S3,
not just the current Pod's local state.

**5. Confirm Alertmanager routing:**

Port-forward to Alertmanager and send a test alert to each channel:

```bash
export KUBECONFIG=~/.kube/devops-pipeline-config
sudo k3s kubectl port-forward -n monitoring svc/monitoring-kube-prometheus-alertmanager 9093:9093 &

curl -XPOST http://localhost:9093/api/v2/alerts -H "Content-Type: application/json" -d '[
  {
    "labels": {"alertname": "TestAppAlert", "team": "app", "severity": "warning"},
    "annotations": {"summary": "Test alert", "description": "Confirms #alerts-app routing."},
    "startsAt": "'"$(date -u +%Y-%m-%dT%H:%M:%S.000Z)"'"
  }
]'

curl -XPOST http://localhost:9093/api/v2/alerts -H "Content-Type: application/json" -d '[
  {
    "labels": {"alertname": "TestInfraAlert", "team": "infra", "severity": "critical"},
    "annotations": {"summary": "Test alert", "description": "Confirms #alerts-infra routing."},
    "startsAt": "'"$(date -u +%Y-%m-%dT%H:%M:%S.000Z)"'"
  }
]'
```

Within about 30 seconds, `TestAppAlert` should appear in `#alerts-app` and
`TestInfraAlert` in `#alerts-infra`.

**6. Confirm the full pipeline across all three environments:**

```bash
curl http://<server-ip>:5000/api/status   # dev
curl http://<server-ip>:5001/api/status   # staging
curl http://<server-ip>:5002/api/status   # production

sudo k3s kubectl get applications -n argocd
```

Each environment should report its own name correctly, and every
`Application` should show `Synced` / `Healthy`.
